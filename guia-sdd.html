Nivel básico

Entender la idea y hacer tu primera spec.

Básico1. ¿Qué es SDD?

Spec-Driven Development es una forma de trabajar en la que, antes de escribir (o pedir) código, escribes una especificación: un documento corto y estructurado que dice qué debe hacer el software y por qué. Después, esa spec se convierte en un plan técnico, el plan en tareas, y las tareas en código.

La diferencia con "escribir documentación" es de jerarquía: en SDD la spec manda. Si el código y la spec no coinciden, uno de los dos está mal y hay que corregirlo. No es un documento que se archiva y se olvida.

La regla de oroSi algo no está en la spec, la IA no debe inventarlo. Si la IA necesita inventarlo, la spec está incompleta: vuelves a la spec, no al prompt.

Las tres preguntas que separan SDD de todo lo demás

PreguntaDónde se respondeQuién la responde
¿Qué y por qué?spec.mdTú (con ayuda de la IA para encontrar huecos)
¿Cómo?plan.mdLa IA propone, tú decides
¿En qué orden?tasks.mdLa IA genera, tú revisas

Básico2. ¿Por qué ahora?

La idea de especificar antes de construir es vieja. Lo nuevo es que los agentes de IA escriben código muy rápido pero tienen tres debilidades que una spec corrige directamente:

Problema del agenteSíntoma en tu día a díaCómo lo corrige la spec
Rellena huecos con suposicionesImplementa paginación que nadie pidió, o se salta validacionesLos no-objetivos y criterios de aceptación delimitan el trabajo
Pierde la intención en sesiones largasA la hora 2 "olvida" una regla de negocio que le dijiste al inicioLa spec es memoria durable: se vuelve a cargar en cada tarea
No sabe cuándo terminó"Listo" sin tests, o con tests que prueban lo que hizo y no lo que pedisteCada criterio de aceptación es una condición verificable de "terminado"

Por eso, en 2025–2026 casi todas las herramientas de IA para código adoptaron alguna variante de este flujo (GitHub Spec Kit, AWS Kiro, OpenSpec, Tessl, BMAD, modos "plan" de los agentes).

Básico3. SDD vs TDD vs BDD vs documentación clásica

No compiten: SDD contiene a TDD y BDD. Lo que cambia es cuál es el artefacto principal.

Documentación clásicaTDDBDDSDD
Artefacto principalDocumento de requisitosTests unitariosEscenarios GherkinSpec + plan + tareas
Escrito paraPersonasEl compiladorNegocio y QAPersonas y agentes de IA
NivelProductoFunción/claseComportamientoFeature completa (qué → cómo → pasos)
¿Se mantiene vivo?Casi nuncaSí (si fallan, rompen el build)SíSí, si lo haces "spec-anchored"
Relación con SDDSu antecesorSe usa dentro de la fase ImplementSus escenarios sirven como criterios en la spec—

Básico4. Los tres niveles de rigor

No todo el mundo que dice "hago SDD" hace lo mismo. Una clasificación útil (popularizada por Birgitta Böckeler en el blog de Martin Fowler) distingue tres niveles:

NivelVentajaRiesgo¿Para ti?
Spec-firstFácil de empezarLa spec se desactualiza en una semanaPara tus primeros 2–3 features
Spec-anchoredLa spec sigue siendo útil meses después; sirve de contexto a la IARequiere disciplina: actualizar spec en el mismo PRObjetivo recomendado
Spec-as-sourceEl código es desechableHerramientas todavía inmaduras; difícil depurarExperimentar, no producción

Básico6. Tu primera spec en 15 minutos

No necesitas instalar nada para empezar. Crea specs/001-nombre-feature/spec.md con esta plantilla mínima:

markdown
# Feature: [Nombre corto]

## Problema
[1–3 frases: qué duele hoy y a quién.]

## Objetivo
[Qué cambia para el usuario cuando esto exista.]

## No-objetivos
- [Lo que explícitamente NO se hará en esta feature.]

## Historias de usuario
- **HU-1 (P1):** Como [rol], quiero [acción], para [beneficio].

## Criterios de aceptación
- **AC-1.1:** Dado [contexto], cuando [acción], entonces [resultado observable].
- **AC-1.2:** ...

## Casos borde
- [Qué pasa si está vacío, duplicado, sin permisos, sin red...]

## Preguntas abiertas
- [NEEDS CLARIFICATION: ...]

Ejemplo rellenado: exportar listado a CSV

markdown
# Feature: Exportar productos a CSV

## Problema
Los administradores copian a mano la tabla de productos a Excel para hacer inventario.

## Objetivo
Descargar en un clic el listado filtrado actual como CSV.

## No-objetivos
- No se exporta a XLSX ni PDF.
- No se programan exportaciones automáticas.

## Historias de usuario
- **HU-1 (P1):** Como administrador, quiero exportar los productos filtrados a CSV,
  para hacer el inventario en Excel.

## Criterios de aceptación
- **AC-1.1:** Dado un filtro "categoría = Bebidas", cuando pulso "Exportar",
  entonces el CSV contiene solo productos de Bebidas.
- **AC-1.2:** El CSV usa UTF-8 con BOM para que Excel muestre bien los acentos.
- **AC-1.3:** Dado un usuario sin rol ADMIN, cuando llama al endpoint, entonces recibe 403.

## Casos borde
- Filtro sin resultados → CSV solo con encabezados.
- Más de 50 000 filas → [NEEDS CLARIFICATION: ¿límite o streaming?]

## Preguntas abiertas
- [NEEDS CLARIFICATION: ¿separador coma o punto y coma?]

Después, en tu agente de IA:

prompt
Lee specs/001-exportar-csv/spec.md.
1) Lista toda ambigüedad o hueco que encuentres (máx. 5 preguntas, ordenadas por impacto).
2) NO escribas código todavía.

✅ Dominas el nivel básico cuando…

  • Puedes explicar la diferencia entre spec, plan y tareas en una frase cada una.
  • Escribiste una spec con no-objetivos y al menos 3 criterios de aceptación.
  • Le pediste a la IA que encontrara huecos en tu spec antes de pedir código.
  • Implementaste una feature pequeña siguiendo esa spec.

Intermedio8. Criterios de aceptación: Gherkin y EARS

Los criterios son la parte más valiosa de la spec: se convierten directamente en tests. Hay dos formatos que funcionan muy bien con IA.

Gherkin (Dado / Cuando / Entonces)Ideal para flujos de usuario y para generar tests de aceptación. Lo conoces de BDD.
EARS (Easy Approach to Requirements Syntax)Ideal para reglas del sistema. Es el formato que usa Kiro. Cinco patrones fijos.

Los 5 patrones EARS

PatrónPlantillaEjemplo
UbicuoEl sistema DEBE …El sistema DEBE almacenar las contraseñas con BCrypt.
Por eventoCUANDO <evento>, el sistema DEBE …CUANDO el usuario solicita recuperar contraseña, el sistema DEBE enviar un enlace válido por 30 min.
Por estadoMIENTRAS <estado>, el sistema DEBE …MIENTRAS la cuenta esté bloqueada, el sistema DEBE rechazar todo inicio de sesión.
No deseadoSI <condición>, ENTONCES el sistema DEBE …SI el token ya fue usado, ENTONCES el sistema DEBE responder 410.
OpcionalDONDE <característica>, el sistema DEBE …DONDE el 2FA esté activo, el sistema DEBE pedir el código tras la contraseña.

Del criterio al test (misma frase, dos formatos)

gherkin
AC-003.1  Token expirado
  Dado un token de recuperación creado hace 31 minutos
  Cuando el usuario envía una nueva contraseña con ese token
  Entonces la respuesta es 410 Gone
  Y la contraseña no cambia

Intermedio9. constitution.md: las reglas que no se negocian

La constitución son los principios del proyecto que toda spec, plan y tarea debe respetar. Se escribe una vez y se cambia rara vez. Es lo que evita que la IA use NgModule en un proyecto standalone o devuelva entidades JPA desde un controlador.

markdown
# Constitución del proyecto

## I. Arquitectura
- Backend: Spring Boot 3, Java 17. Capas: controller → service → repository.
- Los controladores NUNCA exponen entidades JPA; solo DTOs (records).
- Frontend: Angular moderno. Solo componentes standalone. Estado local con signals.
- Nuevo control flow (@if, @for). Prohibido *ngIf / *ngFor en código nuevo.
- UI con PrimeNG + Tailwind. No agregar otra librería de UI.

## II. Contratos
- Toda API REST se define primero en contracts/openapi.yaml.
- Errores con formato RFC 9457 (ProblemDetail).

## III. Calidad (no negociable)
- Test-first: cada criterio de aceptación (AC-x.y) tiene al menos un test con su ID.
- Backend: JUnit 5 + AssertJ; integración con Testcontainers.
- Frontend: tests de componente para cada AC de UI.
- Cobertura mínima de líneas en servicios: 80 %.

## IV. Seguridad
- Nunca registrar en logs contraseñas, tokens ni datos personales.
- Toda entrada se valida con Bean Validation en backend aunque el frontend valide.

## V. Simplicidad
- Sin abstracciones "por si acaso". Máximo 3 capas por feature.
- Agregar una dependencia nueva requiere justificarla en plan.md.

## Gobernanza
- Cambiar esta constitución requiere un PR propio con motivo explícito.
TrucoEscribe reglas que se puedan verificar leyendo el código. "Código mantenible" no se puede verificar; "Sin *ngIf en código nuevo" sí.

Intermedio10. plan.md: el "cómo"

Aquí sí entra la tecnología. La IA lo genera a partir de la spec + constitución, y tú lo revisas como si fuera el diseño de un compañero.

markdown
# Plan técnico: [Feature]

## Resumen
[2–3 frases del enfoque.]

## Contexto técnico
- Backend: Spring Boot 3 / Java 17 / PostgreSQL
- Frontend: Angular (standalone, signals) / PrimeNG / Tailwind
- Dependencias nuevas: [ninguna | X, porque ...]

## Verificación contra la constitución
- [x] Solo DTOs en controladores
- [x] Contrato OpenAPI primero
- [ ] Excepción: ... (justificación)

## Diseño
### Modelo de datos      → ver data-model.md
### Contratos de API     → ver contracts/openapi.yaml
### Componentes frontend → rutas, componentes, servicios
### Flujo                → diagrama de secuencia

## Decisiones y alternativas
| Decisión | Alternativa descartada | Motivo |
|----------|------------------------|--------|

## Riesgos
- ...

## Estrategia de pruebas
- AC-x.y → tipo de test (unitario / integración / componente / e2e)

Qué revisar en un plan generado por IA

  • Dependencias nuevas: ¿de verdad hace falta esa librería?
  • Sobre-ingeniería: patrones Strategy/Factory para un caso con una sola variante.
  • Cobertura: cada historia P1 de la spec tiene un camino en el plan.
  • Estrategia de pruebas: cada AC tiene un tipo de test asignado.

Intermedio13. Ejemplo completo: recuperar contraseña

Una feature real que cruza Angular, Spring Boot, base de datos y correo. Así se ve cada artefacto.

spec.md

markdown
# Feature 002: Recuperar contraseña

## Problema
Los usuarios que olvidan su contraseña escriben a soporte; tardan hasta 24 h en recuperar acceso.

## Objetivo
Recuperar el acceso en menos de 5 minutos sin intervención de soporte.

## No-objetivos
- No incluye recuperación por SMS.
- No incluye cambio de contraseña estando logueado (feature 004).

## Historias
- **HU-1 (P1):** Como usuario que olvidó su contraseña, quiero recibir un enlace por correo.
- **HU-2 (P1):** Como usuario con enlace, quiero definir una nueva contraseña.

## Requisitos (EARS)
- **REQ-001** CUANDO se solicita recuperación, el sistema DEBE responder igual exista o no
  el correo (no revelar cuentas).
- **REQ-002** CUANDO el correo existe, el sistema DEBE enviar un enlace de un solo uso.
- **REQ-003** SI el enlace tiene más de 30 minutos, ENTONCES el sistema DEBE rechazarlo.
- **REQ-004** SI el enlace ya se usó, ENTONCES el sistema DEBE rechazarlo.
- **REQ-005** El sistema DEBE exigir contraseñas de 10+ caracteres con letra y número.

## Criterios de aceptación
- **AC-001.1** Dado un correo inexistente, cuando solicito, entonces recibo 202 y el mismo mensaje.
- **AC-001.2** Dado un correo existente, cuando solicito, entonces se envía 1 correo.
- **AC-001.3** Con el formulario enviado, el botón se deshabilita y aparece el mensaje genérico.
- **AC-003.1** Dado un token de 31 min, cuando confirmo, entonces 410 y la contraseña no cambia.
- **AC-004.1** Dado un token ya usado, cuando confirmo, entonces 410.
- **AC-005.1** Con "abc123", el formulario muestra el error de política y no envía.

## Casos borde
- 5 solicitudes del mismo correo en 1 minuto → solo la primera envía correo.
- Solicitudes nuevas invalidan tokens anteriores del mismo usuario.

## Preguntas abiertas
- (resuelta) ¿Cerrar sesiones activas al cambiar contraseña? → Sí.

Backend: implementación (T005/T006/T010)

java
public record ResetRequest(@NotBlank @Email String email) {}

public record ResetConfirm(
        @NotBlank String token,
        @NotBlank @Size(min = 10)
        @Pattern(regexp = "^(?=.*[A-Za-z])(?=.*\\d).+$") String newPassword) {}

@RestController
@RequestMapping("/api/auth/password-reset")
class PasswordResetController {

    private final PasswordResetService service;

    PasswordResetController(PasswordResetService service) {
        this.service = service;
    }

    /** REQ-001: respuesta idéntica exista o no el correo. */
    @PostMapping
    @ResponseStatus(HttpStatus.ACCEPTED)
    void request(@Valid @RequestBody ResetRequest body) {
        service.requestReset(body.email());
    }

    @PostMapping("/confirm")
    @ResponseStatus(HttpStatus.NO_CONTENT)
    void confirm(@Valid @RequestBody ResetConfirm body) {
        service.confirm(body.token(), body.newPassword());
    }
}

@Service
@Transactional
public class PasswordResetService {

    static final Duration TTL = Duration.ofMinutes(30); // REQ-003
    private static final SecureRandom RANDOM = new SecureRandom();

    private final UserRepository users;
    private final PasswordResetTokenRepository tokens;
    private final MailService mail;
    private final PasswordEncoder encoder;
    private final Clock clock;

    public PasswordResetService(UserRepository users, PasswordResetTokenRepository tokens,
                                MailService mail, PasswordEncoder encoder, Clock clock) {
        this.users = users; this.tokens = tokens; this.mail = mail;
        this.encoder = encoder; this.clock = clock;
    }

    public void requestReset(String email) {
        users.findByEmailIgnoreCase(email).ifPresent(user -> {
            tokens.invalidateAllFor(user.getId());              // caso borde: invalida anteriores
            byte[] raw = new byte[32];
            RANDOM.nextBytes(raw);
            String token = Base64.getUrlEncoder().withoutPadding().encodeToString(raw);
            tokens.save(PasswordResetToken.builder()
                    .user(user)
                    .tokenHash(TokenHasher.sha256(token))
                    .expiresAt(Instant.now(clock).plus(TTL))
                    .build());
            mail.sendPasswordReset(user.getEmail(), token);     // REQ-002
        });
    }

    public void confirm(String token, String newPassword) {
        var entity = tokens.findByTokenHash(TokenHasher.sha256(token))
                .orElseThrow(ResetTokenGoneException::new);
        if (entity.getUsedAt() != null) throw new ResetTokenGoneException();          // REQ-004
        if (Instant.now(clock).isAfter(entity.getExpiresAt())) throw new ResetTokenGoneException(); // REQ-003
        entity.getUser().setPasswordHash(encoder.encode(newPassword));
        entity.setUsedAt(Instant.now(clock));
    }
}

@ResponseStatus(HttpStatus.GONE)
class ResetTokenGoneException extends RuntimeException {}
Detalle pro: inyectar ClockLos requisitos con tiempo (REQ-003) solo son testeables si el tiempo es inyectable. Declara un @Bean Clock clock() { return Clock.systemUTC(); } y en tests usa Clock.fixed(...). Pon esta regla en tu constitución.

                  [loading]="loading()" [disabled]="form.invalid || loading()" />
      }
    </form>
  `,
})
export class ForgotPasswordPage {
  private readonly api = inject(AuthApi);
  readonly form = inject(FormBuilder).nonNullable.group({
    email: ['', [Validators.required, Validators.email]],
  });
  readonly loading = signal(false);
  readonly sent = signal(false);

  submit(): void {
    if (this.form.invalid) return;
    this.loading.set(true);
    this.api.requestPasswordReset(this.form.getRawValue().email).subscribe({
      // Mismo resultado visible en éxito o error de red controlado (REQ-001)
      complete: () => { this.loading.set(false); this.sent.set(true); },
      error: () => { this.loading.set(false); this.sent.set(true); },
    });
  }
}

Avanzado16. SDD sin framework: archivo de instrucciones + prompts

Si prefieres no instalar nada, puedes conseguir el 80 % del valor con un archivo de instrucciones permanente y cuatro prompts reutilizables. El archivo se llama CLAUDE.md (Claude Code), AGENTS.md (Codex y otros) o .github/copilot-instructions.md (Copilot).

markdown
# Instrucciones para el agente

## Flujo de trabajo obligatorio (Spec-Driven)
1. Nunca escribas código de una feature sin `specs/NNN-*/spec.md` aprobada.
2. Si la spec tiene `[NEEDS CLARIFICATION]`, pregunta; no asumas.
3. Antes de implementar, lee: constitution.md, spec.md, plan.md y tasks.md.
4. Implementa UNA tarea de tasks.md a la vez. Márcala [x] al terminar.
5. Cada test lleva el ID del criterio que verifica (AC-xxx.y) en su nombre.
6. Si descubres que la spec es incorrecta o incompleta, DETENTE y propón el cambio
   a la spec antes de seguir.

## Reglas del proyecto
Ver `.specify/memory/constitution.md` (o `docs/constitution.md`).

## Comandos
- Backend tests: `./mvnw test`
- Frontend tests: `npm test -- --watch=false`
- Verificar AC: `./scripts/check-ac.sh`

Los 4 prompts reutilizables

prompt
### 1 · SPECIFY
Actúa como analista de producto. Con la idea de abajo, escribe specs/NNN-<slug>/spec.md
usando la plantilla de specs/_template/spec.md.
- Solo QUÉ y POR QUÉ. Prohibido mencionar frameworks, tablas o clases.
- Criterios con ID AC-xxx.y en formato Dado/Cuando/Entonces.
- Marca toda duda como [NEEDS CLARIFICATION: ...] en vez de suponer.
Idea: <describe la feature>

### 2 · CLARIFY
Revisa spec.md como un QA escéptico. Hazme máximo 5 preguntas, una a la vez,
priorizando las que cambiarían el diseño. Tras cada respuesta, actualiza la spec.

### 3 · PLAN
Con spec.md y constitution.md, escribe plan.md, data-model.md y contracts/openapi.yaml.
Incluye: verificación contra la constitución, decisiones con alternativas descartadas,
y estrategia de pruebas por AC. No escribas código de implementación.

### 4 · TASKS + IMPLEMENT
Genera tasks.md: tareas de ≤1h, ruta de archivo, test antes de implementación,
[P] si es paralelizable, agrupadas por historia. Luego implementa SOLO T001
y detente para revisión.

Avanzado17. SDD en proyectos existentes (brownfield)

La mayoría del trabajo real es modificar código que ya existe y que nunca tuvo specs. La estrategia es en dos pasos: documentar la verdad actual y luego especificar solo el cambio (delta). Es el modelo de OpenSpec.

Prompt de retro-spec

prompt
Analiza backend/src/main/java/.../auth y frontend/src/app/auth.
Escribe specs/baseline/auth/spec.md describiendo el comportamiento ACTUAL
(no el ideal) en formato EARS con IDs REQ-AUTH-xxx.
- Cita el archivo y método donde se implementa cada requisito.
- Si encuentras comportamiento que parece un bug, NO lo corrijas: lístalo
  en una sección "Sospechas" al final.

Formato de delta (estilo OpenSpec)

markdown
# Cambio: add-2fa  →  changes/add-2fa/specs/auth/spec.md

## ADDED Requirements
### Requirement: Código 2FA tras contraseña
DONDE el usuario tenga 2FA activo, el sistema DEBE pedir un código TOTP tras la contraseña.
#### Scenario: código correcto
- Dado un usuario con 2FA, Cuando ingresa contraseña y código válidos, Entonces inicia sesión

## MODIFIED Requirements
### Requirement: REQ-AUTH-002 Inicio de sesión
(texto completo actualizado del requisito)

## REMOVED Requirements
### Requirement: REQ-AUTH-007 "Recordarme" por 90 días
Motivo: reemplazado por sesiones de 30 días con 2FA.
Por qué deltasRevisar un PR de spec que dice "ADDED / MODIFIED / REMOVED" es tan claro como revisar un diff de código. Al terminar, el delta se fusiona en la spec base y esta vuelve a ser la verdad actual.

✅ Dominas el nivel avanzado cuando…

  • Usaste Spec Kit u OpenSpec (o tu flujo manual) en una feature real.
  • Tu repo tiene un CLAUDE.md / AGENTS.md que obliga al flujo SDD.
  • Generaste una retro-spec de un módulo existente y la validaste.
  • Hiciste un cambio en código existente usando un delta de spec.

Pro18. Contract-first: el OpenAPI como parte de la spec

Una spec en prosa puede malinterpretarse; un contrato OpenAPI no. En nivel pro, el contrato se escribe en la fase Plan y genera las interfaces de Spring y el cliente de Angular. Si backend o frontend se desvían, no compila.

// El controlador implementa la interfaz generada: si el contrato cambia, no compila.
@RestController
class PasswordResetController implements PasswordResetApi {
    private final PasswordResetService service;
    PasswordResetController(PasswordResetService service) { this.service = service; }

    @Override
    public ResponseEntity<Void> requestPasswordReset(ResetRequest body) {
        service.requestReset(body.getEmail());
        return ResponseEntity.accepted().build();
    }

    @Override
    public ResponseEntity<Void> confirmPasswordReset(ResetConfirm body) {
        service.confirm(body.getToken(), body.getNewPassword());
        return ResponseEntity.noContent().build();
    }
}

Pro19. Trazabilidad: de requisito a PR

Con IDs estables puedes responder automáticamente "¿qué test verifica esta regla?" y "¿qué regla justifica este código?".

DóndeConvención
spec.mdREQ-003 (regla), AC-003.1 (criterio verificable)
tasks.mdT009 Test: AC-003.1 …
JUnit@DisplayName("AC-003.1 …") y opcionalmente @Tag("REQ-003")
Angularit('AC-003.1 …')
Commits / PRfeat(auth): valida expiración de token [AC-003.1]

Script: todo AC debe tener al menos un test

bash
#!/usr/bin/env bash
# scripts/check-ac.sh — falla si algún AC de las specs no aparece en ningún test
set -uo pipefail
SPEC_DIR="${1:-specs}"
TEST_DIRS=(backend/src/test frontend/src)

mapfile -t ACS < <(grep -rhoE 'AC-[0-9]{3}\.[0-9]+' "$SPEC_DIR" | sort -u)
missing=0
for ac in "${ACS[@]}"; do
  if ! grep -rqF "$ac" "${TEST_DIRS[@]}" --include='*Test.java' --include='*IT.java' --include='*.spec.ts' 2>/dev/null; then
    echo "❌ $ac no tiene test"
    missing=$((missing + 1))
  fi
done

if [ "$missing" -eq 0 ]; then
  echo "✅ ${#ACS[@]} criterios de aceptación cubiertos"
else
  echo "⚠️  $missing de ${#ACS[@]} criterios sin test"
  exit 1
fi

Pro20. Quality gates en CI

La disciplina no escala con buena voluntad; escala con automatización. Estos gates convierten la spec en algo que rompe el build si se ignora.

yaml
# .github/workflows/sdd-gates.yml
name: SDD gates
on: pull_request

jobs:
  spec-gates:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }

      - name: Gate 1 · El PR referencia una spec
        env: { BODY: "${{ github.event.pull_request.body }}" }
        run: |
          echo "$BODY" | grep -qE 'specs/[0-9]{3}-' \
            || { echo "El PR debe enlazar su carpeta specs/NNN-*"; exit 1; }

      - name: Gate 2 · Contrato sin cambios incompatibles
        run: |
          git show origin/${{ github.base_ref }}:contracts/openapi.yaml > /tmp/base.yaml
          docker run --rm -v "$PWD:/w" -v /tmp:/t tufin/oasdiff \
            breaking /t/base.yaml /w/contracts/openapi.yaml --fail-on ERR

      - name: Gate 4 · Todo AC tiene test
        run: bash scripts/check-ac.sh

  tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: '17', cache: maven }
      - name: Gate 3 · Backend
        run: cd backend && ./mvnw -B verify
      - uses: actions/setup-node@v4
        with: { node-version: '22', cache: npm, cache-dependency-path: frontend/package-lock.json }
      - name: Gate 3 · Frontend
        run: cd frontend && npm ci && npm test -- --watch=false

Pro21. Specs vivas y control del drift

Drift es cuando código y spec dicen cosas distintas. Es inevitable; lo que importa es detectarlo rápido.

PrácticaCómo
Spec en el mismo PRSi cambia el comportamiento, el diff incluye spec.md. Sin excepción.
Auditoría con IAPeriódicamente: "Compara specs/002 con el código actual. Lista diferencias como: spec dice X / código hace Y / archivo:línea".
ADRs para el "por qué" técnicoLas decisiones de plan.md que afectan a todo el sistema se promueven a docs/adr/NNNN-titulo.md.
Specs cerradas vs vivasLas carpetas specs/NNN son el historial; la spec consolidada por módulo (baseline) es la verdad actual.
Feedback a la constituciónSi corriges a la IA dos veces por lo mismo, esa corrección se vuelve regla en la constitución.
markdown
# docs/adr/0007-tokens-de-recuperacion-hasheados.md
## Estado
Aceptado — 2026-11-02

## Contexto
Feature 002 requiere enlaces de recuperación de un solo uso (REQ-002, REQ-004).

## Decisión
Guardar solo SHA-256 del token; el token en claro solo viaja en el correo.

## Consecuencias
+ Una fuga de la BD no permite usar tokens.
− No se puede reenviar el mismo enlace; se genera uno nuevo.

RetrabajoNúmero de "no, eso no era" por feature. Debe bajar.
